## A. 계획 실행 시 발생할 수 있는 문제 (심층)

### A1. 골든 코퍼스는 "정답"이 아니라 "현행 출력"이다 — Phase 0의 구조적 한계

`jobs/`의 content.json은 현행 파서의 산출물이므로 **현행 버그를 그대로 포함**한다. 스냅샷 테스트는 "바뀌지 않았음"을 증명할 뿐 "올바름"을 증명하지 못한다. 더 까다로운 건 그 반대 상황: Phase 1~2의 개선이 **의도적으로** 현행과 다른(더 나은) 출력을 낼 때마다 골든 갱신 여부를 사람이 판단해야 한다. 이 판단이 잦으면 "테스트가 늘 빨갛다 → 무시한다"로 흐른다.

**대응**: (a) 비교를 필드 단위로 — 내용 필드(텍스트·순서)는 엄격, 부가 필드는 관대. (b) 골든 승격 절차: diff 리포트를 보고 "의도된 개선"만 명시적 승인 커밋. (c) Phase 2부터 골든 대조와 별개로 **속성 검증**(원고 단어셋 보존, 문항수 일치 등 정답 없이도 참인 속성)을 병행 — 이쪽은 갱신 피로가 없다.

### A2. InDesign이 자동화 검증의 천장이다

parse-only 회귀는 1분에 돌지만, 조판(E2E) 회귀는 iMac+InDesign 필수에 본질적으로 flaky하다: 모달 다이얼로그 하나(폰트 누락, 링크 갱신)로 무인 배치 전체가 멈추고, InDesign 크래시·메모리 누수(장시간 배치 시)도 현실 리스크.

**대응**: E2E는 엔진당 1건 smoke 수준으로 축소하고 주력 검증은 텍스트 덤프 대조(Phase 4)로. 야간 배치 전 `UserInteractionLevels.NEVER_INTERACT` 강제 + InDesign watchdog(재시작 스크립트)을 배치의 전제조건으로 먼저 구축.

### A3. v2→v1 변환기 = 비문서화된 14개 스키마의 리버스 엔지니어링

v1 content.json 스키마는 엔진마다 다르고 문서가 없다. 변환기가 어떤 암묵 필드를 놓치면 JSX는 에러 없이 그 데이터를 무시한다 — **조용한 레이아웃 회귀**. 또 이중 스키마 유지 기간에는 수정이 두 배로 든다.

**대응(범위 축소 확정)**: 전 엔진 v2 전환은 여름 목표에서 공식 제외. v2는 파일럿 2개(workbook Step3 + 신규 동형 엔진)만. 나머지 12개 엔진은 Phase 1(공용 추출)의 보호만 받고 v1 그대로 둔다. 변환기는 파일럿 엔진 1개분만 작성.

### A4. JSX 공용화는 이번 여름 가장 위험한 수술이다

14개 run.jsx는 "거의 같지만 미묘하게 다르다"(스타일명, 분기, 프레임 처리). 공통 함수로 추출하다 미묘한 차이를 하나 놓치면 레이아웃이 조용히 달라지는데, **이건 텍스트 대조 검수로 잡히지 않는다**(내용은 같으니까). 시각 회귀를 자동 검증할 수단이 현재 없다(PDF 픽셀 비교는 폰트 렌더·날짜 노이즈로 실용성 낮음).

**대응(범위 축소 확정)**: **기존 엔진의 run.jsx는 이번 여름에 건드리지 않는 것이 기본값.** 공용 JSX 코어(lib.jsxinc)는 신규 동형 엔진에서만 검증하고, 기존 엔진 이전은 2학기 이후 성수기 아닌 시점에 한 엔진씩. Phase 3의 "14개 통합"은 "코어 제작 + 신규 1개 적용"으로 축소.

### A5. template_spec 자동 추출은 "구조"까지, "의미"는 못 뽑는다

.indd에서 스타일·마스터·프레임 인벤토리는 자동으로 나오지만, "이 프레임이 지문번호 자리"라는 **의미**는 기계가 알 수 없다. 신규 내지 등록은 "완전 자동"이 아니라 "자동 추출 + 사람의 1회 라벨링(~30분)"이다. 여전히 현행(InDesign 열어 역추적 + 코드 수정)보다 훨씬 낫지만 기대치를 정확히 하자.

### A6. 95% 분류율의 산수 — "교재 단위 무개입"은 산술적으로 어렵다

문항 100개 교재에서 미분류 5%면 권당 5문항은 사람 몫이다. 서술형 분류율이 객관식보다 낮아 서술형 비중 큰 학교는 체감이 더 낮다. 목표를 "무개입"이 아니라 **"개입의 국소화"**(기계가 문항 단위로 지목 → 그 문항만 처리)로 정의해야 실망하지 않는다. 블라인드 테스트 지표도 "교재 무개입률"보다 **"문항 자동처리율 + 지목 정확도"**가 옳은 지표다.

### A7. 일정 — 6~7주는 풀타임 기준이고, 방학에도 교재는 만든다

여름 특강 교재·파이널 제작이 병행되면 실 가용 시간은 절반일 수 있다. 또 운영 환경 특성상: auto git pull(5분 간격)·auto-commit이 main에 계속 쌓이는 상태에서 장기 브랜치를 운용하면 merge 충돌이 누적된다 (iMac↔맥북 2기기 동기화까지 겹침).

**대응**: Phase 순서 = 하방 확보 순서이므로 시간 부족 시 뒤를 자른다. Phase 0에서 auto-commit 정책 조정(개편 브랜치 제외 or 메시지 개선) + 주 1회 main→summer-2026 sync를 루틴화.

### A8. 검수 게이트의 초기 오탐 기간 — alarm fatigue가 최악 시나리오

가동 초기에는 오탐(정상인데 ⚠️)이 많아 "지목 지점 확인"이 전량 검수보다 피곤할 수 있다. 오탐이 누적되면 사람이 리포트를 무시하게 되고, 그 순간 검수 게이트는 없느니만 못하다.

**대응**: 등급제 도입 — 초기엔 ❌(내용 누락·정답 잔존 등 치명)만 차단성 경고로, ⚠️는 정보성으로. 오탐률을 매주 측정해 ⚠️ 항목을 점진 승격. 신뢰 형성까지 2~4주 튜닝 기간을 일정에 명시.

### A9. 리뷰어 부재 — 테스트 품질이 전체 품질의 상한

1인 조직 + AI 주도 대량 변경 구조에서 사람 코드리뷰가 없으므로, 검증은 Phase 0 테스트에 전적으로 의존한다. 즉 **Phase 0을 대충 하면 이후 전부가 모래 위**다. 회귀가 2학기 성수기에 발견되면 복구 비용이 가장 크다.

**대응**: pre-overhaul 태그로 상시 롤백 가능 유지. 2학기 첫 2주는 병행 운영(신 경로 조판 + 문제 시 구 경로 즉시 복귀). 성수기 직전 대형 merge 금지 — 개학 1주 전 코드 프리즈.

### A10. 범위 크리프 — "고치고 싶은 것"이 12개+

조사에서 나온 문제를 전부 여름에 고치려는 유혹. 여름 목표는 "어떤 원고가 와도 깨지지 않는 조판"이지 "완벽한 코드베이스"가 아니다. app.py 분리·git 위생·인증 구조는 조판 품질에 직접 기여하지 않으므로 C섹션의 별도 트랙(틈새 시간)으로 관리하고 Phase에 섞지 않는다.

## B. 현실적 기대효과

### 확실한 것 (Phase 0~1만 끝나도 확보되는 하방)

| 효과 | 근거 |
|---|---|
| **"조용한 원고 손실" 사고 종결** | silent-skip 전면 로그화 + 내용보존 가드 전 엔진 적용. 단락이 빠졌는데 "성공" 보고되는 현행 최대 품질 리스크가 제거됨 |
| **수정 공포 해소** | 회귀 검증 수 시간(수동) → 1분(pytest). "고치면 다른 데가 깨질까봐" 못 고치던 구조가 끝남. AI 주도 수정의 안전판 |
| **추출 계층 버그의 순환 차단** | 밑줄·특수문자·섹션 누락류는 1곳 수정 = 전 교재 반영. "A 고치면 B 재발"이 이 계층에서는 구조적으로 불가능해짐 |

### 조건부 (Phase 2~4 완료 시)

- **검수 노동의 전환**: 전 페이지 훑기 → 기계가 지목한 문항만 확인. 튜닝 안착 후 검수 시간 50~70% 감소 예상. 단 초기 2~4주는 오탐 때문에 오히려 증가할 수 있음(A8).
- **새 발문 표현 대응 비용**: 코드 수정+재배포 → 데이터 1줄 추가. 비개발자(조교)도 가능한 작업이 됨.
- **지문번호 수동 입력 제거**: 파일럿 엔진부터. 전 엔진 확산은 2학기 과제.
- **신규 교재 추가 비용 급감**: 동형 모의고사 엔진이 검증되면, "새 교재 = 새 엔진 코딩"이 "새 교재 = 매핑 데이터 작성"이 됨 → 더 많은 학교/교재 수주 여력. 특장점(자동화) 자체가 상품성이 됨.

### 기대하면 안 되는 것 (정직한 한계)

- **"사람 0명" 조판** — 미분류 문항(권당 수 개), 표/이미지 원고, 레이아웃 미세 조정은 여전히 사람 몫. 얻는 것은 개입의 **예측 가능화·국소화**다.
- **여름 내 14개 엔진 전면 전환** — 파일럿 2개가 현실적 상한. 나머지는 공용 추출 + 검수 게이트의 보호만 받는다 (그것만으로도 가치 큼).
- **조판 미학 개선** — 이번 개편은 인식·검수의 개선이지, 기존 JSX가 만드는 레이아웃 품질 자체는 그대로다.

## C. 계획 외 — 방학 동안 고칠 수 있는 것 / 고치면 좋은 것

### C1. Quick wins (각 반나절~1일, 개편 틈새에)

1. **requirements.txt 실체화** — 현재 `flask`만 명시인데 실제로 `openpyxl`, `PyMuPDF(fitz)`, `numpy` 사용 확인. 새 기기/재설치 시 재현 불가 상태. Python 버전도 명시.
2. **jobs/ 보존 정책** — 6.2GB, 정리 로직 없음. 골든 코퍼스 승격 후 "90일 초과 아카이브" cron. HANDOFF 보류 항목인 iCloud 옛 폴더 5.3GB 정리도 함께.
3. **업로드 견고화** — `secure_filename` 미사용, MAX_CONTENT_LENGTH 1GB(과대). 파일명 정규화 + 확장자 화이트리스트 + 상한 하향.
4. **조판 완료/실패 알림** — 현재 사용자가 로그를 봐야 결과를 앎. 잡 종료 시 macOS 알림/메일 훅 1개면 "돌려놓고 잊기"가 가능해짐.
5. **auto-commit 메시지 개선** — `auto(iMac): <시각>` → 변경 파일 요약 포함. git 히스토리가 처음으로 디버깅 도구가 됨.

### C2. 중간 규모 (2~5일, 일부는 개편의 인프라)

6. **스테이징 환경** ★개편과 직결 — 현재 Flask 재시작 = 즉시 실서비스 배포. 포트 5011에 스테이징 인스턴스 + 배포 스크립트(테스트 통과 시에만 kickstart). 개편 기간 내내 안전판이 됨.
7. **InDesign watchdog** ★개편과 직결 — 미실행/크래시 감지 + 자동 재시작 (.claude/TODO.md에 이미 계획됨). Phase 4 야간 E2E 배치의 전제조건.
8. **사용자/권한 구조** — admin/assistant 2명 하드코딩 → data/users.json. 조교 온보딩(HANDOFF 보류) 대비.
9. **app.py 블루프린트 분리** — 1,652줄 58라우트를 도메인별 분리, `_run_pipeline`을 core로. 위험 낮고 이후 모든 작업의 작업성 향상. 단 Phase와 섞지 말고 별도 커밋.
10. **수동 JSX ↔ 엔진 JSX 이원화 정리** — `조판/인디자인 스크립트/`의 수동 스크립트와 엔진 JSX가 같은 패턴의 두 계보. 최소한 "어느 쪽이 최신 로직인지" 매핑 문서화, 장기적으로 공용 코어로 흡수.

### C3. 큰 것 (1주+, 여름 후반 여유 시 또는 2학기)

11. **단일 iMac 의존 완화** — 조판 서버+InDesign+원본 .indd가 한 대에. "iMac이 오늘 죽으면 며칠 만에 복구 가능한가"를 리허설: 원본 .indd/data/.env 백업 검증, 복구 절차 문서. (풀 이중화가 아니라 복구 시간 단축이 목표)
12. **관측성 대시보드** — 엔진별 성공률/실패 추이/오버플로우 통계. 검수 게이트(Phase 4) 데이터가 쌓이면 자연히 가능해지는 후속물.
13. **yonestudio.com 접근 제어** — Cloudflare Access 또는 IP 제한. 현재 비밀번호 로그인만으로 인터넷 전체에 노출.

### 권장 편성

- **개편 Phase에 흡수**: 6(스테이징), 7(watchdog)은 사실상 개편 인프라 → Phase 0~1 기간에 함께.
- **틈새 처리**: 1, 2, 4, 5는 대기 시간(InDesign 배치 중 등)에 소화.
- **여름 후반 판단**: 3, 8, 9, 10은 Phase 4까지 순항 시에만.
- **2학기로**: 11, 12, 13.
