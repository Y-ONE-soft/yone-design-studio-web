검수 게이트를 만들거나 "있다"고 보고하기 전에, **실제로 새어 나갔던 사례를 넣어 fail 이 나는지** 보고 **정상 책 전체에서 헛경보가 0인지** 본다. 사용자: *"수정만 하지 말고 오류 원인 분석하고 앞으로 두번 다시는 안 일어나도록 코드 수정해야 돼"* (2026-09-11, 광문1 2차 검수).

**Why:** 포켓북 G-P13(원문 대비 잘림)은 `return None` 빈 껍데기에 부르는 곳도 없었는데 "있다"고 믿어 2강 분석 잘림이 2차 검수까지 나갔다. 다시 만든 첫 판은 22권에서 헛경보 20건, 동시에 진짜 사례는 놓쳤다(해석 속 영어 이름이 글자열을 오염). 회귀 시험 없이 "통과"만 보고 넘어갈 뻔했다.

**How to apply:** ① 사고 사례 원문을 기준선으로 떠 두고(`parse_before.json` 식) 고친 뒤 전후 대조 — 바뀐 지문이 의도한 것뿐인지. ② 게이트는 옛 데이터로 fail·새 데이터로 pass 둘 다 확인. ③ 대조를 **못 한** 건수를 로그에 낸다(조용한 통과 금지). ④ 파일 패치는 **구문 확인 후 쓰기**(`ast.parse` 먼저) — 자동 커밋 훅이 깨진 파일을 즉시 커밋·푸시한다(c59043ab). 관련 [[project_pocketbook_gwangmun_2609]]
