## 0. 진단 요약 — 무엇이 문제인가

사용자가 지적한 5가지 문제를 코드 전수 조사로 검증했고, 전부 실재하며, 추가로 7가지를 더 확인했다.

### 지적된 문제 (전부 확인됨)

| # | 문제 | 코드 근거 |
|---|---|---|
| 1 | **리터럴 규칙 의존** — 원고가 조금만 바뀌면 미인식 | `workbook/parser.py:612` `_RE_MANUSCRIPT_HEADER`가 교재명 8종을 이름으로 하드코딩("마더텅", "Reading Power"...). `_RE_PAGE_MARKER`는 L/p/U 3형식만. 발문 어미 5종만 인식(`:1193`). 정답 표기 1형식만 제거(`:1114`) → 새 표기는 정답이 교재에 노출 |
| 2 | **내지 파일 이해 부재** — 지문번호 등 수동 입력 | .indd 템플릿의 기계가독 스펙이 없음. 마스터/페이지/스타일 구조를 사람이 InDesign에서 열어 역추적해 config·stepStoryMap에 수기 기입. 스타일명·헤더 정규식·마스터명("A","O")이 JSX에 하드코딩 |
| 3 | **검수 부재** — 조판되면 끝 | 전 엔진의 `verify()`가 "파일 존재 + 오버플로우 수치"만 검사. **원고 내용이 빠짐없이/올바른 스타일로 들어갔는지 검증하는 코드 0줄**. 테스트 프레임워크 0. 파이널의 `_validation_warnings`가 유일한 예외(경고만) |
| 4 | **공통 규칙 미포착** — 한 교재 수정이 다른 교재에서 재발 | `core/base.py` 223줄 vs 엔진 파서 총 2.5만 줄. 밑줄 추출 함수가 3곳에 복붙(workbook:111/blackbook:39/seseospecial). 원문자 정규화(➀→①)는 mockexam에만 존재. run.jsx 14개가 전부 독립 사본(3,257~3,763줄) → 공통 버그는 14곳 패치 |
| 5 | **원고 구조 이해 부재** — 세세한 룰 집착 | 단어 기반 매칭이 주류. 단, **해결의 재료는 이미 있음**: `engines/_taxonomy`(146 leaf 유형, 126,312 발문 분석, Step3 분류율 95.2%) + `조판/원고_분류체계/` 14개 설계 문서(공통 문항 스키마, 단락종류 10종 시그니처, 스타일 매핑 매트릭스). **문제는 어떤 엔진도 이걸 import하지 않는 것** |

### 핵심 통찰

> **5월에 이미 정답을 설계해 놓고 연결하지 않았다.**
> `조판/원고_분류체계/05_파서_룰_매핑표.md`의 공통 문항 스키마, `09_단락종류.md`의 구조 시그니처,

> 이번 여름의 일은 "새로 발명"이 아니라 **"설계도를 코드에 연결 + 안전망 구축"**이다.

## 1. 목표 아키텍처 (To-Be)

```
원고(docx/hwp/hwpx)
   │
   ▼
[A] 공용 추출 계층  core/extract/          ← 파일 포맷만 담당. 엔진 무관
   │   단락+밑줄+마커 raw 추출, 원문자/특수문자 정규화, 손실 0 보장(보존 가드)
   ▼
[B] 구조 인식 계층  core/structure/        ← "이 단락은 무엇인가"
   │   단락종류 판정(GH/Q/P/C/Cond/Box/Word/K/A — 다층 시그니처)
   │   + 발문 유형 분류(engines/_taxonomy, 146 leaf)
   ▼
[C] 표준 문항 IR   content.json v2         ← 05_파서_룰_매핑표 공통 스키마
   │   {type, kind, header, question, stimulus, given, choices, constraints}
   ▼
[D] 렌더 계층      템플릿 스펙 + 매핑 테이블 + 공용 JSX 코어
   │   template_spec.json(.indd에서 자동 추출) × style_map.json(11번 문서)
   ▼
[E] 검수 게이트    core/inspect/
       조판 결과 텍스트를 다시 뽑아 IR과 대조 → 내용보존/문항수/스타일/overflow 리포트
```

원칙:
- **구조가 룰보다 우선**: "(A)가 선지 위에 오면 선지 스타일" 같은 단어 룰 대신, "발문 뒤·선지 앞의 짧은 라벨 단락은 선지 그룹 소속" 같은 위치+마커+언어+길이 조합 판정 (09번 문서의 다층 방어 방식). 새 표기 `[가]`가 와도 구조로 잡힘.
- **룰은 코드가 아니라 데이터**: 발문 패턴·스타일 매핑·헤더 형식을 전부 JSON/YAML로 외부화. 룰 추가 = 데이터 1줄, 재배포 불필요.
- **모든 룰은 코퍼스로 검증**: 7,900 원고·126,312 발문 코퍼스에 룰 변경을 돌려 분류율 회귀를 수치로 확인 후 반영.

## 2. 주차별 계획

> 각 Phase는 독립적으로 가치가 있고, 중간에 방학이 끝나도 그 시점까지의 결과물이 그대로 운영에 쓸 수 있게 설계했다.
> **모든 Phase의 완료 조건에 "회귀 스냅샷 전건 통과"가 포함된다.**

### Phase 0 — 안전망 (방학 첫 주, 대수술 전 필수)

수술보다 마취·모니터가 먼저다. 이번 개편의 성패는 "바꿔도 깨지지 않았음을 기계가 증명"하는 데 달렸다.

1. **골든 코퍼스 구축**: `jobs/` 585건 + `테스트 파일/`에서 엔진별 대표 원고 세트 선별(엔진당 3~10건, 학교·교재·연도 다양성 확보) → `tests/corpus/`에 원고+기대 content.json 쌍으로 고정.
2. **parse-only 스냅샷 테스트**: pytest 도입. `engine.parse()`만 실행(InDesign 불필요 → CI 가능)해 content.json이 골든과 일치하는지 비교. `python3 -m pytest tests/`가 1분 내 전 엔진 회귀 검증.
3. **git 위생**: auto-commit launchd에 diff 요약 메시지 추가, 개편 작업은 `summer-2026` 브랜치에서 진행 후 단계별 merge. 태그 `pre-overhaul` 생성.
4. **현행 스펙 동결 문서**: 엔진별 "지금 실제로 되는 것/안 되는 것" 1페이지 스펙 (검수 기준선).

5. **스테이징 + watchdog 편입 (리스크분석 C 6·7)**: 포트 5011 스테이징 인스턴스(테스트 통과 시에만 실서비스 kickstart) + InDesign 미실행/크래시 감지 watchdog — Phase 4 야간 배치의 전제조건이므로 안전망 단계에서 함께 구축.

**산출물**: `tests/` + 골든 코퍼스 + pre-overhaul 태그. **이후 모든 변경은 이 테스트를 통과해야만 merge.**

> **[2026-07-03 운영 결정]** 개편 코드는 별도 워크트리(`~/dev/yone-design-web-summer`, 브랜치 `summer-2026`)에서 작업한다. 이유: `scripts/autosync.sh`가 launchd로 3분마다 이 체크아웃에서 `git add -A` + 자동커밋 + `pull --rebase origin main` + push를 수행하므로, main 체크아웃에서 장시간 작업하면 리베이스가 작업 중 파일을 간섭한다. 문서(docs/)는 main에 두어 autosync로 양 기기 공유, 코드는 워크트리에서 마일스톤 단위 merge.

### Phase 1 — 공용 추출 계층 (1.5주)

문제 4·6 해소. 가장 기계적이고 위험이 낮아 첫 수술로 적합.

1. `core/extract/` 신설: docx/hwp/hwpx 단락+밑줄+세그먼트 추출을 workbook 파서(가장 성숙)의 구현 기준으로 단일화. 다중 section 처리(blackbook 버그 수정판), dot-디렉토리 가지치기 포함.
2. **정규화 단일화**: 원문자 dingbat(➀→①), `^8`, HTML 엔티티 등 mockexam에만 있던 정규화를 공용층으로 → 전 교재 동일 적용.
3. **silent-skip 전면 제거**: 모든 `except: continue`에 경고 로그 + 카운터. `_warn_step3_content_loss` 패턴(원고 단어셋 vs 출력 단어셋 대조)을 공용 함수로 승격, 전 엔진 parse 끝에 자동 실행.
4. 엔진별 치환은 **한 엔진씩**, 스냅샷 테스트 통과 확인 후 다음 엔진 (버그 수정 격리 규칙 준수).

**산출물**: `core/extract/`, 전 엔진이 이를 import, 추출 중복 코드 삭제. 효과: **밑줄/특수문자 버그 수정 1곳 = 전 교재 반영.**

### Phase 2 — 구조 인식 + 표준 IR (2주, 개편의 심장)

문제 1·5·7 해소.

1. **`core/structure/` 신설**: 09번 문서의 단락종류 10종 다층 시그니처(위치+마커+컨텍스트+언어+길이)를 구현. 단어 리터럴 매칭은 시그니처의 한 층일 뿐, 단독 판정 근거가 되지 않게.
2. **_taxonomy 실전 투입**: 발문마다 `classify()` 호출해 leaf 코드 부여. 미분류 발문은 경고로 수집(조용히 넘어가지 않음). 룰은 `rules.py` → 데이터 파일로 이전.
3. **content.json v2 (표준 IR)**: 05번 문서의 공통 스키마를 JSON Schema로 확정 + 검증기. 신규 파이프라인은 v2를 쓰고, 기존 엔진 JSX가 기대하는 v1은 **v2→v1 변환기**로 생성 → 기존 JSX 무수정 운영 가능 (strangler-fig).
4. **코퍼스 검증 루프**: 룰/시그니처 변경 시 126,312 발문 코퍼스에 자동 재분류 → 분류율·변화 diff 리포트. "새 원고 데이터를 많이 읽고 규칙을 잡는다"의 상시 자동화.
5. 파일럿 엔진 1개(workbook Step3 권장 — 이미 95.2% 분류율)를 v2 경로로 전환해 검증.

> **[2026-07-03 범위 확정]** 전 엔진 v2 전환은 여름 목표에서 **공식 제외**. v2는 파일럿 2개(workbook Step3 + 신규 동형 엔진)만. v1 스키마가 엔진마다 다르고 비문서화라 변환기가 리버스 엔지니어링이 되는 리스크 때문 (리스크분석 A3). 나머지 12개 엔진은 Phase 1의 공용 추출 + Phase 4의 검수 게이트 보호만 받는다.

**산출물**: 구조 인식기 + IR 스키마 + 검증기 + 코퍼스 리그레션 도구. 효과: **선지 위 `[가]`가 와도 구조로 인식. 새 발문 표현 = 데이터 1줄 추가.**

### Phase 3 — 내지(템플릿) 계층 (1.5주)

문제 2·12 해소.

1. **템플릿 스펙 자동 추출**: .indd를 열어 마스터·페이지·스토리·텍스트프레임·단락/문자 스타일 인벤토리를 `template_spec.json`으로 덤프하는 JSX 제작 (mockexam/analysis의 중단된 `extract_indd_data.jsx` 재활용). 신규 내지 등록 = 이 스크립트 1회 실행, 사람의 역추적 제거.
2. **JSX 하드코딩 외부화**: 스타일명·헤더 패턴·마스터명을 `.settings.json` 주입으로 전환. 학교별 차이는 JSX 사본이 아니라 매핑 데이터 차이로.
3. **공용 JSX 코어**: 공통 함수(스토리 탐색, GREP, overflow, 프레임브레이크, 로그)를 `core/jsx/lib.jsxinc`로 추출, `prepare_jsx`가 빌드 시점에 concat하여 임시 run.jsx 생성 (ES3 제약 회피).

> **[2026-07-03 범위 확정]** **기존 엔진 14개의 run.jsx는 이번 여름에 수정하지 않는다** (리스크분석 A4 — 미묘한 분기 유실로 인한 레이아웃 회귀는 텍스트 대조로 검출 불가). 공용 JSX 코어는 신규 동형 엔진에서만 검증하고, 기존 엔진 이전은 2학기 이후 비수기에 한 엔진씩.
4. **지문번호/출처 자동 기입**: IR의 `header.source`(변형 차원에 이미 정의됨)를 템플릿 스펙의 대상 프레임에 자동 삽입 — 현재 수동 입력 노동 제거.

**산출물**: template_spec 추출기 + 공용 JSX 라이브러리 + 설정 주입화. 효과: **내지 교체/신규 학교 = 데이터 작업, 코드 수정 0.**

### Phase 4 — 검수 게이트 (1주)

문제 3 해소. "조판되면 끝"을 "검수 통과해야 끝"으로.

1. **조판 결과 텍스트 회수**: 조판 직후 JSX가 스토리별 전체 텍스트+적용 스타일을 `typeset_dump.json`으로 덤프.
2. **자동 대조**: IR ↔ 덤프 비교 — (a) 내용 보존(문항·선지·지문 단어셋), (b) 문항 수/선지 수, (c) 단락스타일이 style_map과 일치, (d) overflow 상세(어느 스토리 몇 번째 문항인지), (e) 정답/해설 잔존 검사.
3. **검수 리포트 UI**: job 결과 페이지에 ✅/⚠️/❌ 리포트. 실패 항목은 페이지·문항 단위로 지목 → 사람은 전량 검수가 아니라 **지목된 곳만 확인**.
4. E2E 회귀: 골든 코퍼스 일부를 실제 InDesign 조판까지 돌리는 야간 배치(iMac) + 리포트.

**산출물**: 검수 게이트 + 리포트. 효과: **사람 검수가 "전 페이지 훑기" → "기계가 지목한 지점 확인"으로.**

### Phase 5 — 실전 파일럿 + 마무리 (1주 + 버퍼)

1. **블라인드 테스트**: 코퍼스에 없는 신규/과년도 원고 20~30건을 무수정 투입 → 무개입 성공률 측정, 실패는 전부 룰 데이터 보강으로 해결되는지 확인(코드 수정이 필요했다면 아키텍처 결함으로 기록).
2. **동형 모의고사 신규 엔진**(12번 문서 설계 기반)을 새 아키텍처 위에서 제작 — "새 교재 추가가 정말 쉬워졌는가"의 리트머스.
3. 문서화: 새 아키텍처 가이드, 룰 데이터 추가 절차(비개발자용), CLAUDE.md 갱신.
4. 2학기 운영 전환: `summer-2026` → main merge, 구 경로 병행 운영 2주 후 구 코드 제거 결정.
