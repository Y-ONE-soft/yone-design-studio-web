| mockexam 스타일명 | 분류 체계 대응 | 비고 |
|---|---|---|
| `_meta` | (메타) | 학교/시험 헤더 등 |

## A. 단락 종류 식별 시그니처 (mockexam 기존 vs 분류 체계)

### 발문 분류 (mockexam 기존 로직)

```python
# 우선순위 순 (parser.py:323~360)
1. _RE_INTRO_READ        → "다음 글을 읽고"
2. _RE_INTRO_CHOOSE      → "문제 번호" (객관식)
3. _RE_INTRO_DESC        → "서술형 번호" (서술형)
4. _RE_INTRO_OBJ         → "문제 번호" (한글 + ?)
```

**분류기 통합 시 강화 포인트**:
| 기존 정규식 | 한계 | 분류기 통합 후 |
|---|---|---|
| `_RE_INTRO_READ` ("다음 글을 읽고") | 변형 발문 못 잡음 | `classify() == OBJ-LNG-HEADER` 모든 변형 자동 |
| `_RE_INTRO_OBJ` (한글 + ?) | "찾으시오" 같은 명령형 못 잡음 | leaf 코드 매칭 = 무조건 발문 |
| `_RE_INTRO_DESC` ("시오"로 끝) | 서술형 발문 일부만 | `SRV-*` 코드 매칭 = 서술형 |

### 박스 기대 결정 (mockexam의 `_set_box_expectation`)

발문이 어떤 종류인지에 따라 다음 단락이 어떤 박스인지 결정 — **이게 워크북-B (leaf 코드별 부속 구조)와 동일한 개념**.

| 발문 패턴 (mockexam 정규식) | mockexam 박스 결정 | 분류 체계 leaf 코드 |
|---|---|---|
| `주어진 문장이 들어가기에 가장 적절한` | `테두리_순서삽입` 박스 기대 | `OBJ-FLW-INSERT` (변형 포함) |
| `이어질 글의 순서로 가장 적절` / `주어진 글 다음에 이어질` | `테두리_순서` 박스 기대 | `OBJ-FLW-ORDER` / `OBJ-FLW-ORDER-NEXT` |
| `한 문장으로 요약` / `요약문` / `요약하고자 한다` | `pending_summary` (↓ 마커 대기) → `테두리_요약` | `OBJ-FLW-BLANK-AB` / `SRV-WRT-SUMM` |
| `질문의 답` | `pending_qa` → Q&A 박스 | (분류 체계 외 — 특수 학교 변형) |

**분류기 통합 시 강화**:
- mockexam의 박스 결정 로직 4개를 leaf 코드 직접 매칭으로 대체 가능
- 새 변형(`OBJ-FLW-INSERT-MARK` 등)도 자동 적용

### Cond / Box 마커 (mockexam의 `_RE_CONDITION` / `_RE_EXAMPLE`)

mockexam 기존 정규식:
```python
_RE_CONDITION = re.compile(r"^\s*[<\[\(ㅣ│\|]?\s*조\s*건\s*[>\]\)ㅣ│\|]?\s*\.?\s*$")
_RE_EXAMPLE   = re.compile(r"^\s*[<\[\(ㅣ│\|]?\s*보\s*기\s*[>\]\)ㅣ│\|]?\s*\.?\s*$")
```

이미 **다양한 마커 표기(`<>`, `[]`, `()`, `ㅣㅣ`, `||`)를 처리**. 분류 체계의 `[보기]/[조건]` 정규화 룰과 호환.

## B. leaf 코드별 부속 단락 구조 (세미모의)

mockexam은 이미 발문 → 다음 단락 박스 결정 로직이 있어 워크북-B 표를 거의 그대로 적용 가능.

### 표준 세미모의 발문 흐름

```
[문제 번호 / 서술형 번호 / 다음 글을 읽고]   ← Q / Q-SRV / Q-INTRO
  ↓
[지문 / 테두리_순서삽입 / 테두리_순서]       ← P / P-CONTEXT
  ↓ (필요 시)
[테두리_요약 / 테두리_보기 / 테두리_조건]    ← Box / Cond
  ↓
[선지 / 서술형답지]                        ← C / A
```

### leaf 코드별 mockexam 단락스타일 매핑

| 분류 체계 leaf 코드 | 기대되는 mockexam 단락 시퀀스 |
|---|---|
| `OBJ-CTN-TITLE` / `TOPIC` / `GIST` / `CLAIM` / `PURPOSE` / `MOOD` / `TONE` | `문제 번호` → `지문` → `선지`×5 |
| `OBJ-CTN-MATCH` / `MATCH-NEG` | `문제 번호` → `지문` → `선지`×5 |
| `OBJ-FLW-ORDER` | `문제 번호` → `테두리_순서` → `지문_순서`×3 ((A)(B)(C)) → `선지`×5 |
| `OBJ-FLW-INSERT` | `문제 번호` → `테두리_순서삽입` → `지문` → `선지`×5 |
| `OBJ-FLW-IRRELEVANT` | `문제 번호` → `지문` (인라인 ①~⑤) → `선지`×5 |
| `OBJ-FLW-BLANK-SENT` | `문제 번호` → `지문` (빈칸) → `선지`×5 |
| `OBJ-FLW-BLANK-AB` | `문제 번호` → `지문` → `테두리_요약` → `선지`×5 |
| `OBJ-VOC-PAREN` / `GRM-PAREN` | `문제 번호` → `지문` (인라인 (A)(B)(C)) → `선지`×5 |
| `OBJ-VOC-UND-WRONG` / `GRM-UND-WRONG` | `문제 번호` → `지문` (밑줄 ①~⑤) → `선지`×5 |
| `OBJ-LNG-MULTI` 묶음 | `다음 글을 읽고` → `지문` → `문제 번호`×N → `선지`×5 each |
| `SRV-WRT-COND` | `서술형 번호` → `지문`? → `테두리_조건` → `서술형답지` |
| `SRV-WRT-SUMM` | `서술형 번호` → `지문` → `테두리_요약` → `서술형답지` |
| `SRV-GRM-FIX-MARKED` | `서술형 번호` → `지문` (ⓐ~ⓔ 밑줄) → `서술형답지` |

## D. 분류기 통합 강화 효과 (제안 — 적용은 별도)

### 현재 mockexam parser의 한계

mockexam parser는 다음과 같은 fragile 케이스에서 깨진다:
1. **새 발문 변형**: 정규식에 없는 발문 표현 → 발문으로 인식 못 함 → 지문으로 잘못 분류
2. **변형 마크**: `[보기]` / `(보기)` / 다른 변형 → 일부는 잡지만 분류 체계만큼 견고하지 않음
3. **leaf 코드 정보 없음**: 발문이 잡혀도 어떤 유형인지 모르므로 학교별 미세 변형 처리 어려움

### 분류기 통합 시 강화

```python
# 현재 mockexam (parser.py:355)
if _RE_INTRO_OBJ.search(stripped):
    return "문제 번호"

# 분류기 통합 후 (제안)
code, label, kind = classify(stripped)
if kind == "객관식":
    return "문제 번호"  # 같은 결과
if kind == "서술형":
    return "서술형 번호"
# fallback (분류 안 됐지만 발문 형태일 가능성)
if _RE_INTRO_OBJ.search(stripped):
    return "문제 번호"
```

이런 식으로 **분류기를 1차 시도, 기존 정규식을 fallback**으로 두면:
- 신규 발문 변형은 분류기가 잡음
- 기존에 잡히던 케이스는 fallback으로 보장
- 회귀 위험 최소

### 박스 기대 결정 강화

```python
# 현재 mockexam (parser.py:242)
def _set_box_expectation(ctx, stripped):
    if _RE_BOX_INTRO_INSERT.search(stripped):
        ctx["expect_box"] = "테두리_순서삽입"
    # ...

# 분류기 통합 후 (제안)
def _set_box_expectation(ctx, stripped):
    code, _, _ = classify(stripped)
    if code in ("OBJ-FLW-INSERT", "OBJ-FLW-INSERT-MARK"):
        ctx["expect_box"] = "테두리_순서삽입"
    elif code in ("OBJ-FLW-ORDER", "OBJ-FLW-ORDER-NEXT", "OBJ-FLW-CONNECT-SEQ"):
        ctx["expect_box"] = "테두리_순서"
    elif code in ("OBJ-FLW-BLANK-AB", "SRV-WRT-SUMM", "SRV-WRT-SUMM-COND", "SRV-WRT-SUMM-THEME"):
        ctx["pending_summary"] = True
```

→ **새 변형 leaf 코드(예: `OBJ-FLW-ORDER-NEXT`)가 추가되면 자동으로 적용**되므로 mockexam parser 수정 불필요.

## E. 신규 단락 종류 (분류 체계 발견)

광범위 추출로 mockexam에 없던 새 단락 종류 발견:

| 새 단락 종류 | leaf 코드 | mockexam 처리 추가 권장 |
|---|---|---|
| Box-TF (T/F 보기) | `OBJ-CTN-TF` | T/F 박스 (테두리_T/F? 또는 테두리_보기 alias) |
| C-COMBO (조합 선지) | 흐름/내용 다수 | 기존 `선지` 스타일에 인라인 처리 |
| P-CONTEXT-DIALOG (대화문) | `OBJ-LNG-DLG` | 새 박스 (테두리_대화)? |
| Q-K (우리말 라인) | `SRV-WRT-KO-EN` 등 | 새 스타일 (우리말 발문)? |

이건 새 학교/새 시험기간 원고 들어왔을 때 추가 검토 대상.

## F. 통합 단계 (수정 X — 분석만)

**Tier 0 (지금)**: 분석 결과만 문서화 ← 현재
**Tier 1 (안정 후)**: mockexam parser에 분류기 fallback 추가 (정규식 1차 → 분류기 보조)
**Tier 2 (검증 후)**: 분류기 1차 → 정규식 fallback (역전)
**Tier 3 (충분히 검증 후)**: 정규식 제거, 분류기 단독
